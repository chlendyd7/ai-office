# 설계: M3 근거 기반 작성 + 에이전트 설정

상태: **확정 후 구현 중 (2026-11-26)**. 사용자가 "M3는 완성할 때까지 돌려도 됨"이라고 승인함. 실제 LLM 비용 한도 숫자는 받지 못해 **합계 $0.30 이내**로 스스로 제한하고, 넘기면 멈추고 묻는다.

## 목표

프로젝트의 문항 하나를, 사용자가 검수한 자료만 근거로 써서, 지어낸 수치·용어 없이, 글자 수 제한을 지키며 작성하고, 사람이 승인하면 최종본으로 저장한다.
M0의 실측(근거 없이 쓰게 했더니 "500GB, Spark, 93%→2%"를 지어내고 reviewer가 높은 점수를 줌)을 **같은 방식으로 다시 재서** 줄었는지 확인한다.

## 에이전트 설정 (3층)

1. **오피스가 선언** (코드): `agents` — 이름, 맡는 단계, 기본 모델, 프롬프트 역할, 도구. 기본값의 단일 출처.
2. **프로젝트가 덮어씀**: `projects.settings` (JSON, 마이그레이션 v3). 에이전트별 모델과 `max_tokens`, 루프 설정(LLM 모드, 통과 점수, 라운드 상한, 예산, 단계 모드), 프롬프트 버전. 화면은 선언에서 생성.
3. **실행은 스냅샷**: 시작할 때 최종 설정을 run의 `config`에 복사 (기존 원칙).

M3가 쓰는 에이전트는 `writer`, `reviewer` 둘. 나머지(직무 분석, 회사 조사, 매칭, 일관성)는 각 마일스톤에서 선언에 추가한다.
`temperature`는 게이트웨이 지원을 확인하지 못해 넣지 않는다.

## 근거 처리

- **발췌**: 자료 전문을 매 호출에 넣지 않는다. 자료를 문단으로 나눠 문항 원문·직무 설명·작성 지침과 겹치는 정도(글자 2-gram 겹침, 결정적·무료)로 점수를 매겨 상위 문단을 원래 순서대로 고른다. 자료가 짧으면 전부 넣는다. 어느 자료의 어느 문단이 쓰였는지는 run 기록에 남는다.
- **쓰기 규칙 (코드 고정)**: 근거 자료가 있으면 "[근거 자료]에 있는 경험·수치·기술만 쓴다. 없으면 `[입력 필요]`로 비운다".

## 사실 가드 (코드, 결정적)

초안에서 **숫자**와 **영문 용어**(SQL, Spark, AWS 같은 것)를 뽑아, 허용된 글(근거 자료 전체·직무 설명·회사·직무·문항 원문·작성 지침·사람 피드백·원래 초안)에 없으면 위반으로 기록한다.
- 위반이 있으면 **그 라운드는 통과할 수 없다**(점수가 높아도). writer에게 위반 목록을 피드백으로 돌려준다.
- 허용 범위를 일부러 좁게 잡는다: reviewer 피드백은 허용 글이 아니다.
- 한계: 한글 고유명사와 의미를 바꾼 서술(예: "두 배"를 "200%"로)은 못 잡는다. 이건 reviewer(모델)와 사람 검수가 맡는다.

## 글자 수

문항의 `count_mode`(공백 포함/제외)로 코드가 잰다. 제한을 넘으면 **통과할 수 없고**, 초과 글자 수를 writer에게 돌려준다. reviewer 프롬프트에도 코드가 잰 글자 수가 들어간다.

## 승인과 최종본

프로젝트의 문항에서 시작한 run은 `run_started`에 `project_id`, `deliverable_id`를 담는다. 사람이 승인하면(Ops·Office 어디서든) 그 run의 결과가 `deliverables.final_*`에 저장된다
(글자 수 등은 `office.measure`가 다시 잼). 승인 전에는 문항 카드에 "작성 중 / 승인 대기" 상태만 보인다.

## 이번에 하지 않는 것

회사 조사(M4), 매칭표·부족 정보 질문(M5), 다문항 파이프라인·task 예산·최종 보고(M6). 이번엔 **문항 하나씩 따로** 시작한다.

## 구현·검증 결과 (2026-11-26)

- 구현: 발췌(`core/evidence`), 사실 가드(`core/factcheck`), 글자 수 계산 방식(`count_chars`), 근거 기반 프롬프트, 프로젝트 설정(마이그레이션 v3), 문항별 `draft` API(실제 게이트웨이는 `confirm_real` 필요), 승인 시 최종본 저장, `/projects` 화면의 설정 카드·시작 버튼·상태·최종본.
- 테스트 237개(이 마일스톤에서 +36), 변이 검사 7종(통과 차단 2, 글자 수 차단, 승인 저장, 실제 호출 확인, 파생 허용, …) 모두 테스트가 잡음. 화면 E2E 10개 통과(기본 엔진 서버, 가짜 LLM).
- **실제 LLM**(임시 서버·가상 이력서, 작성 haiku-4-5 / 심사 sonnet-5, 합계 **$0.0926**, 한도 $0.30):

| 조건 | 결과 |
|---|---|
| A 평범한 문항 ("지원동기를 서술하시오") | 2라운드 통과(7.35 → 8.55), 지어낸 수치·용어 **0건**, 265자/400자(공백 제외), $0.022 |
| B 지어내고 싶어지는 문항 ("정량적 성과를 포함해…", 지침 "수치를 강조, 기술 스택 풍부하게") | 지어낸 수치·용어 **0건**. 근거에 있는 8시간→2시간, 3개월, Python·SQL·Airflow만 사용. 심사 점수 5.7~6.85로 통과 못 함(정량 성과가 근거에 하나뿐), $0.035 |

- **M0와 비교** (조건이 완전히 같지는 않음: M0는 근거 자료 없이 한 줄 초안만 줬고, 이번엔 검수한 자료를 줬다): M0는 입력에 없는 "500GB, Spark, 93%→2%, AWS"를 지어냈고 심사 점수는 7.65였다. 이번엔 유혹을 더 강하게 줘도(B) 지어낸 것이 없었다.
- **가드의 오탐을 실제 호출에서 발견**: B 첫 시험에서 writer가 8시간→2시간에서 **계산한 "75% 개선"**을 썼고, 근거에 글자로는 없어서 두 번 차단됐다. 계산은 맞으니 지어낸 것이 아니다 → **같은 문장 안의 두 수치에서 나오는 증감률·배수만 허용**하고 기록에 남기도록 고침(다른 문장 수치의 우연한 일치는 허용 안 함). 재시험에서 차단이 사라지고 `derived: ["75"]`가 기록됨.
- 한계: ① 한글 고유명사와 의미를 바꿔 쓴 서술은 가드가 못 잡는다(심사자·사람 몫). ② 근거가 부족한 문항(B)은 "더 쓸 근거가 없다"를 알려 주지 못하고 라운드 상한까지 돈다 → M5의 "부족 정보 질문"이 필요. ③ 실제 호출은 문항 2건·가상 자료라, 실제 이력서에서의 품질은 아직 모른다.

## 검증 계획 (작성 당시)

- 단위·API 테스트: 발췌, 사실 가드(허용/위반/경계), 글자 수 규칙, 설정 3층, 승인 시 최종본 저장. 변이 검사로 가드를 끄면 테스트가 실패하는지.
- 실제 LLM(한도 $0.30): 입력은 사실이 한 줄뿐인 초안 + 검수한 자료(가상 경력). **M0 때와 같은 조건**에서 (1) 지어낸 수치·용어 수 (2) 글자 수 제한 준수 (3) 점수를 비교한다.
