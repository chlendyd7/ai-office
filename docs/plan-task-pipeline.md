# 계획: 리소스 기반 자소서 Task 파이프라인

> **용어 (2026-11-26 확정)**: 아래의 "Task"는 DB·코드에서 **project**(프로젝트, 의뢰 한 건)와 **deliverable**(산출물, 자소서 문항 하나)이다.
> 오피스가 여러 개(취업·코드·기획)가 될 것을 전제로 뼈대는 도메인을 모르게 설계했다 → `design-task-schema.md`.

한 회사·직무 지원을 **하나의 프로젝트**로 관리한다. 사용자의 리소스(이력서·경험 정리)와 직무·회사 정보, 자소서 문항(제목+글자 수)을
받아 **직무·회사에 맞춘 자소서를 쓰고**, 최종본을 사람에게 올려 승인을 기다린다.
상태 표시는 ☐ 예정 / ◐ 진행 / ☑ 완료. 결정 이유와 사고는 `project-notes.md`에 적는다.

## 결정된 것 (2026-11-26)

- 개인정보: 사내 게이트웨이로 이력서·자소서 원문이 가도 문제없음 (사용자 확인)
- 순서: 작성 파이프 먼저(M1~M3) → 그 위에 회사 조사(M4)
- 능력 점검: 게이트웨이는 **이미지 입력과 웹 검색 도구를 지원**함 (M0 점검 결과 참고)
- 개인 데이터는 공개 저장소에 올리지 않는다. 내보내기는 저장소 밖 폴더로.
- **리소스는 DB에 저장**(M1 그대로). 원본 PDF·이미지는 저장하지 않는다. 사적 영역의 경계는 "데이터가 들고 다니지 않는 것" — `data/`·`data_export/`·`.env`는 git 무시, 내보내기는 git 폴더 거부,
  잠금 테스트(`test_data_stays_local.py`)가 `.gitignore`가 풀리면 실패시킨다. (이력서 내용은 어차피 실행 기록의 프롬프트로 DB에 들어가므로 "리소스만 DB 밖"은 경계가 되지 못함)
- **PDF·이미지 → 텍스트 변환 규칙**: 쪽 단위로 글자 층이 정상이면 무료(pypdf), 글자 층이 없거나 **깨졌으면** 그 쪽만 LLM(PDF 직접 전송 / 이미지). TXT·MD는 변환 없음.
- **LLM 변환 결과는 "검수 전"** 상태로 저장하고, 사람이 확인해야 task에서 근거로 선택할 수 있다. 변환 호출은 토큰·비용을 기록하고 건당 상한을 둔다(계측 우회 금지).

## 파이프라인

```
① 입력 수집 → ② 직무 분석 → ③ 회사 조사 ──[확인 게이트 A]
→ ④ 매칭표 + 부족 정보 질문 ──[확인 게이트 B]
→ ⑤ 문항별 작성 루프 ×N (기존 write→review→decide + 근거 가드)
→ ⑥ 문항 간 중복·일관성 점검 → ⑦ 최종 보고 (사람 승인 대기)
```

원칙(기존과 동일): 각 단계는 이벤트로 기록 · 사용한 리소스와 조사 결과는 task가 **복사해 스냅샷** · AI는 확정하지 않음 ·
Office에는 원문(리소스, 프롬프트, 응답)을 보내지 않고 진행도·합계·결과만.

## 빠진 것을 반영한 설계 항목

- **근거 가드**: 리소스 = `근거 자료`. 초안의 숫자·고유명사가 리소스나 직무 설명에 있는지 **코드가 결정적으로 검사**. 없으면 사용자에게 묻는다.
- 부족한 정보는 `[입력 필요]`로 모아 한 번에 질문하는 **사람 입력 게이트** (④)
- **직무↔경험 매칭표**: 요구역량마다 근거 리소스와 부족한 부분 (④, 사용자가 확인·수정)
- 회사 조사: 출처 URL·날짜 기록, 작성 전 사용자 확인, 웹 내용은 **데이터이지 지시가 아님**(프롬프트 인젝션 방어). 검색 결과 토큰이 크므로 비용 한도 필요
- 이미지·PDF는 **확인·교정 가능한 텍스트로 변환해 저장** (잘못 읽은 내용이 근거로 쓰이지 않게)
- **발췌**: 리소스 전문을 매 호출에 넣지 않고 문항별로 관련 근거만 선택. 예산은 run 단위에 더해 **task 단위**로도
- 문항 여러 개: 소재 분배(같은 경험 반복 방지), 문항 유형별 프롬프트·루브릭(라이브러리 재활용)
- 루브릭에 "회사 핏", "근거 일치" 항목. 글자 수는 코드(구현됨)
- 최종 보고서: 문항별 최종본·글자 수·점수·사용 근거·미해결 빈칸, 복사·내보내기, Office "task 완료 대기"
- 중단·재개·부분 재실행(회사 조사만, 문항 하나만)
- 이 파이프라인이 앞서 예정했던 **두 번째 워크플로를 대체**. 폼·큐 입력을 `input_fields` 선언 기반으로 전환

## M0 점검 결과 (2026-11-26, 사내 게이트웨이, haiku-4-5)

- **이미지 입력: 지원.** 한글 채용공고 스크린샷을 한 글자도 틀리지 않고 옮겨 적음. 입력 182 / 출력 50 토큰(≈ $0.0004). 이미지 드롭은 별도 OCR 없이 구현 가능.
- **웹 검색 도구(`web_search_20250305`): 지원.** 도구를 주기만 하면 모델이 "검색 불필요"로 쓰지 않을 수 있어, 회사 조사는 `tool_choice`로 **검색을 강제**해야 함.
  강제하니 실제 검색이 1회 일어나 최신 뉴스를 돌려줌(`server_tool_use.web_search_requests: 1`).
- **비용 주의**: 검색 1회가 입력 토큰 **약 18,900개**를 붙임 (≈ $0.02 haiku, sonnet은 약 2배). 응답 `usage`에는 포함되지만,
  호출 전 예산 가드의 추정(`len(prompt)//2 + max_tokens`)에는 안 잡힘 → M4에서 **검색 허용 몫을 최악 추정에 더해야 함**. 검색 건당 별도 요금이 있는지는 대시보드 대조로 확인 필요.
- **PDF 직접 전송(`document` 블록): 지원** (2026-11-26 추가 점검). 글자 있는 2쪽 PDF → 글자 그대로 일치(입력 3,338 / 출력 111 토큰, ≈ $0.0039).
  **그림만 있는 PDF**(글자 층 없음)도 글자 그대로 읽음(입력 1,659 / 출력 22, ≈ $0.0018). 쪽을 이미지로 렌더링할 필요가 없어 PDF 렌더링 라이브러리 불필요.
  규모 감: 쪽당 입력 약 0.8~1.7k 토큰 → 5쪽 이력서 변환은 haiku 기준 약 $0.01~0.02(추정). 두 호출 합계 ≈ $0.0057.
- **M1b 실제 변환 결과** (2026-11-26, 우리 코드 경로 전체, haiku-4-5): 그림만 있는 PDF 1쪽 — 글자 그대로 일치, 입력 1,896 / 출력 32, $0.0021 (최악 추정 3,000 토큰 이내).
  이미지(채용공고) — 4개 항목 모두 일치하고 제목을 `#`으로 구조화, 431 / 62, $0.0007. 혼합 PDF(정상+빈 쪽+깨진 쪽) — 정상 쪽은 글자 층 그대로, 나머지 2쪽만 전송, 3,908 / 918, $0.0085 (사전 상한 표시 $0.0235). 합계 $0.0113.
  **한계**: 깨진 쪽 픽스처는 화면에도 무작위 한글이 그려져 있어 모델이 보이는 대로 옮겼다. 실제로 글자 층만 깨진 PDF(보이는 글자는 정상)에서 복구되는지는 **실제 샘플로 확인하지 못했다**(분류 판별은 검증, 복구는 미검증).
- 점검 3회 합계 ≈ $0.023 (예고한 $0.01 초과 — 검색 결과 토큰 때문, 위 비용 주의 참고).
